# 文件对文件 SQL 语义比对

用于把一个文件作为主文件，和另一个文件做 SQL 语义匹配。

目标不是比较字符串像不像，而是判断：
- 是不是同一业务 SQL
- 对应的是对比文件哪一条 SQL
- JOIN / WHERE / GROUP BY / 子查询 / 过滤条件发生了什么变化
- 为什么认为它们是同一条或不是同一条业务 SQL

这里的执行逻辑推荐拆成三段：
- 预处理：读取 Excel、清洗 SQL、候选召回
- 智能体判断：只负责语义判断
- 后处理：汇总智能体结果并生成最终 Excel

预处理和后处理可以由 Python 或平台节点完成，但它们都 **不直接调用大模型**。

## 适用场景

- 两个 Excel 文件之间做 SQL 批量匹配
- 主文件逐条去对比文件中找对应 SQL
- Excel 可能是标准 `.xlsx`
- Excel 也可能是 HTML 导出的 `.xls`

## 输入

必须输入：
- 主文件
- 对比文件

可选输入：
- 主文件 SQL 列名
- 对比文件 SQL 列名
- 主文件主键列名，比如 `任务编号`
- 候选召回数量 `top_k`

如果没有明确给 SQL 列名，优先自动识别这些列名：
- `SQL语句`
- `SQL`
- `sql`
- `任务详情`
- `慢SQL`

主文件主键列只用于结果定位，不参与 SQL 语义判断。  
例如 `任务编号`、`治理单号`、`需求ID`，便于最后把匹配结果回写到主文件业务记录。

## 总体流程

### 第 1 步：读取两个文件

读取主文件和对比文件的第一张表。

要求：
- 识别表头
- 识别 SQL 列
- 保留原始行号
- 如果有主键列，也一并保留

如果文件是 HTML 导出的 `.xls`：
- 按 HTML 表格方式读取
- 第一行如果是表头，则作为列名

### 第 2 步：清洗 SQL

对 SQL 做轻量清洗，但不要改变业务语义：
- 去掉注释
- 合并多余空白
- 保留原 SQL 作为展示字段
- 生成用于分析的标准化 SQL

### 第 3 步：主文件逐条处理

对主文件中的每一条 SQL，执行以下流程：

1. 提取结构特征
2. 在对比文件中做候选召回
3. 把候选逐条交给智能体做语义判断
4. 汇总智能体结果
5. 选择最优候选作为最终匹配结果

## 结构特征提取

每条 SQL 至少提取这些信息：
- 核心表
- JOIN 数量
- WHERE 条件
- GROUP BY 字段
- SELECT 字段样本
- 子查询数量
- UNION 数量
- 是否包含 WITH / CTE

这些特征只用于候选召回和辅助判断，不直接替代智能体结论。

## 候选召回

为了避免主文件每条 SQL 都和对比文件全部 SQL 做逐条智能体比较，先做一轮候选召回。

召回时优先考虑：
- 核心表重合度
- WHERE 条件重合度
- SELECT 字段重合度
- GROUP BY 重合度
- JOIN 数量差异
- 子查询数量差异

输出 `top_k` 个候选进入智能体判断。  
默认 `top_k = 3`。

## 智能体判断任务

对“主 SQL + 候选 SQL”逐对判断，要求智能体不要做字符串相似度判断，而是做业务语义判断。

### 判定标准

认定为 `同一业务SQL`：
- 查询目标一致，只是写法不同
- 核心表一致，JOIN 结构只是改写或拆分
- WHERE 主干一致，只是参数字面值、日期条件、条件下推不同
- GROUP BY 口径一致，只是字段顺序、别名或聚合写法调整
- 子查询、CTE、UNION 只是结构优化，不改变业务含义
- 分表、分区表、历史表替换，但业务逻辑不变

认定为 `可能同一业务SQL`：
- 查询目标大体一致，但过滤条件或统计口径有部分变化
- 核心表一致，但 JOIN 路径变化较明显
- 看起来像同一业务线上的演进版本，但证据不足以完全确认

认定为 `非同一业务SQL`：
- 查询目标明显不同
- 核心表、核心过滤逻辑、统计口径明显不同
- 一个是列表查询，另一个是统计、更新、通知、归档等不同业务动作
- 差异已经影响业务含义，而不只是写法变化

## 智能体提示词

把下面这段作为智能体的主提示词使用：

```text
你是资深 SQL 语义分析专家。你的任务不是看两条 SQL 字符串像不像，而是判断它们是否属于同一业务 SQL。

请严格按照以下标准判断：
1. 重点看查询目标、核心表、JOIN 关系、WHERE 主干、GROUP BY 口径、子查询/CTE/UNION 的业务含义是否一致。
2. 如果只是改写、分页变化、条件下推、历史分表、字段增减、参数字面值差异，通常仍可判为同一业务SQL或可能同一业务SQL。
3. 如果查询目标、统计口径、核心过滤逻辑明显不同，就判为非同一业务SQL。
4. 必须引用我提供的带行号 SQL，指出你主要依据的具体行号。
5. 请用中文输出详细说明。

你必须输出这些字段：
- judgement: 同一业务SQL / 可能同一业务SQL / 非同一业务SQL
- confidence: 极高 / 高 / 中 / 低
- semantic_score: 0 到 1 的评分
- same_business: true / false
- reasoning: 中文详细说明
- join_change: JOIN 结构变化总结
- where_change: WHERE 或过滤条件变化总结
- group_by_change: GROUP BY 或聚合口径变化总结
- subquery_change: 子查询、CTE、UNION 变化总结
- base_line_refs: 主 SQL 主要依据行号
- target_line_refs: 候选 SQL 主要依据行号
- common_tables: 共同核心表列表
- key_differences: 关键差异点列表
```

## 单对 SQL 的智能体输入模板

对每个“主 SQL + 候选 SQL”组合，传给智能体的用户输入建议如下：

```text
主文件 SQL 结构特征：
{base_features}

对比文件 SQL 结构特征：
{target_features}

主文件 SQL（带行号）：
{base_sql_with_line_numbers}

对比文件 SQL（带行号）：
{target_sql_with_line_numbers}
```

其中：
- `{base_features}` 包含主 SQL 的核心表、JOIN 数量、WHERE 条件、GROUP BY、子查询数量等
- `{target_features}` 包含候选 SQL 的同类信息
- `{base_sql_with_line_numbers}` 和 `{target_sql_with_line_numbers}` 必须带行号

## 行号要求

为了让智能体能标注依据，传给智能体前必须先把 SQL 格式化为按行展示：

示例：

```text
001 | SELECT a.order_id, a.user_id
002 | FROM order_info a
003 | LEFT JOIN pay_info b
004 | ON a.order_id = b.order_id
005 | WHERE a.dt = '2026-07-30'
006 | AND b.pay_status = 'SUCCESS'
```

## 每条主 SQL 的最终输出字段

每条主 SQL 最终至少输出这些字段：
- 主文件行号
- 主文件主键值，如果有
- 主文件 SQL
- 对比文件最佳匹配行号
- 对比文件最佳匹配 SQL
- judgement
- confidence
- semantic_score
- same_business
- reasoning
- join_change
- where_change
- group_by_change
- subquery_change
- base_line_refs
- target_line_refs
- common_tables
- key_differences

## 候选明细输出字段

为了可追溯，建议同时保留候选明细：
- 主文件行号
- 对比文件候选行号
- coarse_score
- table_overlap
- where_overlap
- select_overlap
- 智能体 judgement
- 智能体 semantic_score

## 最终输出形式

最终输出建议分成两层，最终交付物默认是 Excel：

### 1. 汇总表

建议包含：
- 主文件路径
- 对比文件路径
- 主文件 SQL 条数
- 对比文件 SQL 条数
- 候选召回数量
- 同一业务SQL 数量
- 可能同一业务SQL 数量
- 非同一业务SQL 数量

### 2. 匹配结果表

一行代表主文件一条 SQL 的最终匹配结果。

建议字段：
- 主文件主键
- 主文件行号
- 主文件 SQL
- 对比文件匹配行号
- 对比文件匹配 SQL
- 判断结果
- 置信度
- 语义评分
- 主 SQL 依据行号
- 候选 SQL 依据行号
- JOIN 变化
- WHERE 变化
- GROUP BY 变化
- 子查询变化
- 详细说明

### 3. 候选明细表

一行代表一次候选比较，用于排查为什么选中了某条 SQL。

## 给用户的自然语言输出格式

适合在平台回答区展示：

```text
主文件第 12 行（任务编号 T001）匹配到对比文件第 88 行。
判断：同一业务SQL
置信度：高
依据行号：主SQL 第 3、5、8 行；候选SQL 第 4、7、9 行
说明：两者都围绕 instruction 主表查询未支付指令，核心过滤条件一致，差异主要在分页写法和子查询改造，因此判定为同一业务 SQL 的优化版本。
```

## 异常处理

如果遇到以下情况，需要明确返回异常信息：

- 文件无法读取
- 未识别到 SQL 列
- 主文件没有有效 SQL
- 对比文件没有有效 SQL
- 某条 SQL 为空
- 智能体未返回结构化结果

## 推荐调用方式

如果平台支持上传两个文件并附加参数，推荐用户这样输入：

```text
请比较这两个 SQL 文件：
主文件：7.23修复慢sql.xlsx
对比文件：慢SQL表_2026_7_30.xls
主文件 SQL 列：SQL语句
对比文件 SQL 列：SQL语句
主文件主键列：任务编号
候选召回数量：3
```

如果用户不清楚列名，也可以这样输入：

```text
请把这两个 Excel 做 SQL 语义比对，主文件逐条去对比文件里找同一业务 SQL，自动识别 SQL 列并输出匹配结果。
```

## 工作流落地建议

如果平台支持节点编排，推荐按下面的顺序落地：

1. 文件读取节点
2. SQL 清洗和特征提取节点
3. 候选召回节点
4. 智能体判断节点
5. 结果汇总节点
6. Excel 生成节点

其中：
- 前 3 步属于预处理
- 第 4 步只做语义判断
- 第 5、6 步属于后处理

这样可以保证：
- Python 或平台脚本节点不直接调用模型
- 智能体只做最擅长的语义分析
- 最终输出稳定为 Excel
